# 웹 UX·기술 설계 v0.2

## 현행 검증판 UI (2026-09-13)

실행 규칙 0.8. 기존 전장·마법·장비·성장에 별도 정식 출격 기록, 고용·상점·예산·명시적 출격 확정, 6계열 마스터리, 수동 3슬롯·출격 준비 복구와 지도 조작을 구현했다. 구현 계약과 구버전 저장 처리·검증 경계는 이 문서 마지막의 0.8 절과 [남은 작업 계획](remaining-work-plan.md)을 따른다. 아래 전체 제품 설계 중 새 장·최종 아트/사운드·기기별 성능 및 사람 플레이 평가는 후속 작업이다.

## 1. 가볍고 선명한 도트 화면

지도는 24×24 논리 픽셀 타일, 유닛은 24×24 또는 24×32. 스프라이트 확대는 nearest-neighbor 정수배 1×/2×/3×, 확대·축소 버튼으로 선택한다. 카메라는 논리 픽셀 단위로 정렬한다. 창 크기에 화면 전체를 강제로 늘리지 않고 맵 뷰포트를 바꾼다. CSS 패널과 글자는 독립적인 해상도로 그린다.

24픽셀은 작은 지도와 제작량을 위한 **본 프로젝트의 선택**이다. 전투 검증판은 2배 표시 시 48픽셀 타일, 20×15 맵이 960×720이므로 상단 UI를 제외한 공간에는 세로 스크롤이 필요하다. 지도를 작게 강제 축소하지 않고 카메라 이동과 목표 바로가기를 제공한다. 기본 지원 창 1280×720 이상, 그 이하에서는 정보 패널을 접는다. 터치 UI·모바일 성능은 별도 검증 전까지 지원을 약속하지 않는다.

아트는 지형 8종 안팎, 전투 검증판 병종 5종, 지휘관 3종부터 시작한다. MVP는 8병종 실루엣과 지휘관 깃발을 재사용한다. 대기 2프레임, 이동 4, 공격 3, 피격 2를 상한으로 잡고 방향은 좌우 반전을 우선한다. 초상화는 검증판에서 사용하지 않는다. 한글 숫자·설명은 가독성 있는 본문 글꼴 16px 이상, 픽셀 폰트는 짧은 제목만 후보로 둔다.

색만으로 정보를 구별하지 않는다. 아군·적군은 바닥 테두리 모양, 지휘관은 깃발, 소속 부대는 번호, 병종은 무장 실루엣으로 구별한다. HP 숫자 1~10은 항상 표시하고, 행동 완료는 체크 아이콘과 채도 감소를 함께 쓴다. 지휘 밖 용병은 끊긴 깃발 아이콘으로 표시한다.

## 2. 전투 화면 구성

```text
┌ 라운드 3 / 아군 ─ 목표·남은 시간 ─ 저장 상태 ─ 설정 ┐
│                                                   │
│        도트 지도                       선택 유닛   │
│        이동·지휘·위협 범위              소속/HP/MP  │
│        다음 증원 위치                  상성·보정   │
│                                       행동 메뉴   │
├ 다음 미행동 유닛 ─ 지휘범위 ─ 적위협 ─ 로그 ─ 종료 ┤
└ 공격 예측: 상대 HP 10→5 / 내 HP 10→10 / 확정·취소  ┘
```

지휘 범위는 테두리, 이동 가능 칸은 면, 적 위협은 해칭으로 구분한다. 기본은 선택 부대 지휘 범위만 표시한다. 특정 적 하나 또는 전체 적의 이동+기본 공격·마법 범위를 토글할 수 있다. 전체 위협 합계는 여러 적의 실제 행동을 보장하는 값이 아니므로 숫자를 합쳐 “확정 피해”로 보여주지 않는다. 선택 공격의 정확한 교전 예측과 적의 다음 행동 가능 범위를 구분한다.

지휘관 이동을 미리 보면 보정이 켜지고 꺼질 소속 용병을 강조한다. 적 지휘관을 공격할 때는 퇴각 예상 용병에 연결 표시를 준다. 인접 회복 예정량과 NPC 다음 이동 칸, 증원까지 남은 라운드는 맵에서 확인할 수 있다.

현행 마법 메뉴는 코어 `knownSpells`의 학습·장비 목록으로 구성한다. `spellTargetTiles`는 장비 사거리와 이동 후 위치를 반영한 중심을 제공하고, `spellArea`·`previewSpell`·`evaluate`가 영향 칸·대상·실제 HP/MP·상태 성공·재배치·재행동·소환·지형 변화를 결정한다. UI는 같은 코어 조회로 예측하며 피해·사거리·부대 소속·착지 가능 여부를 따로 계산하지 않는다. MP 부족·최대 MP 미달·상태 제약·부적절한 대상·유효 대상 없음은 이유를 표시한다. 텔레포트는 대상 부대와 도착 칸을 차례로 선택하고 확정 전 취소는 상태를 바꾸지 않는다.

첫 전투 명령 전에는 장비·마법 편성을 열 수 있다. 장비 패널은 소유/여유 수량·현재 장착·슬롯·변경 전후 유효 능력치·실행 불가 이유를 제공한다. 마법 편성은 학습 가능 목록을 변경하며 장비 소환을 임의 학습하지 못한다. 미라의 원본 최대 MP 9를 유지하고 오브 장착 시 18이므로 고비용 소환의 사용 제한을 숨기지 않는다. 준비도 명령으로 확정·저장하며 첫 `act` 또는 `endPhase` 후에는 변경할 수 없다.

## 3. 조작과 반복 행동 줄이기

| 조작                             | 동작                                                     |
| -------------------------------- | -------------------------------------------------------- |
| 유닛 클릭 → 목적지 → 행동 → 확정 | 한 유닛의 이동·행동을 원자적으로 수행                    |
| 우클릭 또는 Esc                  | 현재 선택 단계 취소, 확정 전 이동은 자유롭게 취소        |
| Tab / Shift+Tab                  | 다음/이전 미행동 유닛, 소속 부대별 고정 순서             |
| Enter                            | 선택한 명령 확정; 아무 선택 없을 때 페이즈 종료하지 않음 |
| C / T                            | 선택 부대 지휘 범위 / 전체 적 위협 토글                  |
| Space                            | 현재 연출 건너뛰기; 추가 게임 명령은 발생시키지 않음     |
| 방향키 / WASD                    | 맵 카메라 이동, 키보드 타일 선택 모드는 별도 포커스      |

미행동 유닛이 남았을 때 페이즈 종료는 남은 유닛 목록과 확인을 보여준다. 경고를 매 공격마다 반복하지 않고 지휘관 사망 예상·보호 대상 진로 막힘 같은 구체적 결과를 예측 패널에 보여준다. 이미 처리 중인 확정 버튼은 비활성화해 중복 입력을 막는다.

용병을 줄이는 대신 병사 10명 클릭을 요구하지 않는다. 후방 부대 전체 이동은 MVP 필수 기능에서 제외한다. 먼저 `다음 미행동 유닛`, `선택 부대 미행동 용병 모두 대기`를 제공하며 일괄 대기는 대상 목록을 보여준 뒤 확정한다. 일괄 대기도 내부적으로 유닛별 명령을 순서대로 검증한다.

준비 화면에서는 지난 편성을 불러와 현재 고용 목록과 예산에 맞는 부분을 보여준다. 예산 초과를 자동으로 결제하거나 임의로 병종 교체하지 않는다. 고용 개수 +/−, 전체 비용, 예상 시작 지휘 범위, 적 상성을 같은 화면에서 본다.

## 4. 연출 속도와 중단 복구

기본 간략 모드는 맵 위 돌진·타격·HP 변화다. 선택 가능한 상세 모드는 물리 공격과 마법에 별도 부대 교전창을 사용한다. 병사별 접근·타격·넉백·병력 감소, 원거리 발사체, 마법 시전과 피해/회복 효과를 재생한다. 단일·반경·부대 마법은 `spellCast`의 마법·중심·대상 목록과 확정 HP 변화로 연출하며, 여러 대상의 결과를 하나의 행동으로 보여준다. 상세는 일반 4.2초/고속 1.5초다. 확정 결과는 같으며 모드 선택과 건너뛰기는 규칙에 영향을 주지 않는다. 간략 교전은 300~500ms 목표이며 상세는 건너뛰기를 제공한다. 병력 HP에 맞는 작은 도트 잔상은 선택적 표현이며 전투 결과를 계산하지 않는다. 화면 흔들림·번쩍임·자동 카메라 추적은 각각 끌 수 있다.

결과 상태가 먼저 확정되고 연출은 그 결과를 읽는다. 스킵하면 이벤트 재생만 완료하고 피해를 다시 적용하지 않는다. 비활성 탭에서는 연출을 멈추고, 복귀 시 최신 확정 상태에 맞춰 화면을 재구성한다. 지휘관 자동 전투는 없다. 미행동 용병은 턴 종료 때 선택한 자동 행동 옵션에 따라 추종·공격한다. 사운드는 최초 입력 후 활성화하고 장별 지연 로딩, 음소거 선택을 보존한다.

## 5. 성능 예산

아래는 **목표이며 측정 결과가 아니다.** 기준 측정 환경은 내장 그래픽 노트북, 8GB RAM, 1280×720, 깨끗한 프로필의 데스크톱 Chrome/Edge로 잡고 실제 CPU·OS·브라우저 버전을 기록한다. Firefox·Safari는 공개 전 별도 실기 검증한다. 네트워크는 다운로드 10Mbps·RTT 100ms·콜드 캐시로 고정한다.

| ------------------------- | --------------------------------------------------- | ---------------------------------------------------- |

## 6. 기술 선택과 코어 경계

초안의 TypeScript + Phaser + React 구조를 유지한다. 렌더러는 Phaser 4 표준 타일맵·스프라이트부터 검증하고, React는 메뉴·정보 패널을 담당한다. 2026-09-08 확인한 [Phaser 공식 다운로드 목록](https://phaser.io/download/phaser4)에는 4.2.1이 게시되어 있다. 실제 설치 버전은 구현 착수 때 재확인해 lockfile에 고정하며, 특정 버전 간 호환성을 검증 없이 가정하지 않는다.

```text
apps/web/                 Phaser 지도, React UI, 입력과 저장
packages/core/            순수 규칙·경로·예측·AI·성장 정산
packages/content/         JSON: 병종·직업·지형·장비·맵·이벤트
packages/schema/          콘텐츠·세이브 스키마와 참조 검증
packages/sim/             고정 국면과 행동 로그 재현
docs/                     현행 설계
```

위 구조의 초기 골격과 전술 연습장을 생성했다. 실제 구현 범위·명령은 [개발 인수인계](handoff.md)와 README를 참고한다. 이 문서 전체가 구현되었다는 뜻은 아니다. 서버는 MVP에 없다. 데이터 원본은 저장소 JSON 하나로 두고, 스프레드시트는 필요할 때 가져오기 도구를 붙인다. 데이터와 시트를 동시에 원본으로 관리하지 않는다.

```text
evaluate(state, command) → 유효성 + 예상 결과
apply(state, command) → { nextState, events, contributionChanges }
UI → 임시 선택 → evaluate → 확정 → apply → 저장 → events 연출
AI → 같은 evaluate/apply 호출
```

현재 명령은 `Act(unitId, path, action)`, `EndPhase`, 전투 전 준비의 `Equip`·`Train`이다. 정식 출격 배치의 `Deploy`는 후속 설계다. 별도 `Move`를 먼저 확정해 이동 취소와 상태가 엇갈리지 않게 한다. 모든 명령은 `commandId`, `expectedRevision`으로 중복·오래된 입력을 거절한다. 배치 단계와 전투 단계에 허용되는 명령도 분리한다.

실제 마법 행동은 `{ type: "cast", spellId, target: { x, y }, destination? }`이며 텔레포트에만 `destination`을 지정한다. 모든 마법은 이동 경로와 함께 원자적으로 검증한다. `Content.spells`와 유닛 `spellIds`가 정의·학습의 원본이고 이전 `canHeal` 전용 플래그는 사용하지 않는다. 기존 `{ type: "heal", targetId }` 명령은 학습한 첫 회복 마법을 같은 코어 조회로 실행하는 데이터 기반 별칭으로 남긴다. 미라에게는 현재 힐 1의 MP·반경이 적용된다. 정상 결과는 `spellCast`와 피해·회복·상태·이동·재행동·소환·지형 변경·제거 이벤트를 내며, 실패 명령은 MP·상태·로그를 바꾸지 않는다.

원작의 이름·일반 마법 MP·기본 범위와 현행 엔진 해석은 구별한다. 반경은 맨해튼, 피해·RES·상태 성공·지속·텔레포트 배치·재행동 제한·소환 능력치/배치는 프로젝트 규칙이다. 효과는 코어에서 실제 처리하되 원작의 완전 재현이라고 표시하지 않는다. 레벨별 범위 성장·직업별 학습/장착 행렬·불확실한 장비 효과는 확인 과제로 남긴다. `effectiveUnit`은 저장된 원본 능력치와 장비·상태에서 유효 값을 산출하며 화면이나 저장에 누적 적용하지 않는다. `terrainChanges`도 이동·전투·AI·Phaser가 공유한다.

코어는 DOM·렌더러·시계·네트워크에 의존하지 않는다. UI 포커스·선택 상태는 저장되는 전투 상태가 아니다. 지휘 범위·위협 맵·경로 캐시는 상태 revision이 바뀌면 무효화한다. 지휘관 이동·사망으로 바뀐 예측을 재사용하지 않는다.

## 7. AI의 계산 한도와 재현

현행 P03a는 콘텐츠의 선택 필드 `scenario.enemyPlans`에 지휘관 ID와 단계별 `fromRound`, `label`, `target`을 두고, 코어에서 현재 라운드의 목표를 조회한다. E2 지휘관과 소속 용병은 1~2라운드에 북쪽 여울 동쪽 `(11,3)`, 3라운드부터 남쪽 호송로 `(11,10)`를 목표로 삼는다. 계획이 없는 E1·E3는 공통 평가와 가까운 상대 접근을 사용한다. 현재·다음 단계 안내는 같은 코어 조회를 UI에서 표시한다.

목표 접근 비용은 `stepCost`를 공유하는 역방향 Dijkstra로 계산한다. 지형별 진입 비용, 보행의 적 점유 차단, 비행의 통과와 착지 제한을 반영한다. 목표가 점유되면 주변 접근을 평가하고, 현재 위치에서 목표 방향의 경로가 연결되지 않으면 가까운 상대 접근 평가로 돌아간다. 경로 비용은 이동 후보의 점수이며 명령 허가를 대신하지 않는다. 실제 도달 칸과 행동은 기존 `reachable`·`evaluate`·`apply`가 결정한다. 행동 하나마다 전장 상태를 다시 읽으며, 시계나 별도 AI 저장 상태를 참조하지 않는다.

현행 후보는 도달 가능한 칸×공격·대기·정비·학습 마법의 유한 전체 집합이다. 마법은 MP가 충분한 학습 마법의 사거리 내 중심을 열거하고 같은 `previewSpell`·`evaluate`로 검증한다. 1수 평가에 목표까지 남은 비용, 피해·반격·상성·지휘 보정, 지휘관 처치 시 퇴각 전력, 부상 용병의 지휘관 인접 복귀, 지휘관 정비와 현재 사거리 위협을 반영한다. 마법 피해·동시 격파·MP 비용과 부상 아군 회복도 평가하며 위급한 지휘관 지원을 높게 본다. 용병을 지휘관보다 먼저 움직이고 유닛 ID, 이동 비용·좌표, 행동 열거 순서로 동률을 고정한다. 한 페이즈에 유닛당 확정 행동 1개 후 종료한다. 현재 맵의 적 학습 목록은 비어 있어 기존 적 행동 후보는 유지된다.

후속 설계는 부대별 목표 선택과 협동 회복, 1차 점수 상위 12개 후보의 2수 탐색, 성격별 정수 JSON 가중치다. E1의 다리 돌파·지휘관 단독 돌입 억제와 E3의 호송대·궁병 우선 목표도 아직 구현하지 않았다. 확장 시 동률은 부대 ID → 유닛 ID → 목적지 `(y,x)` → 행동 타입 → 대상 ID 순을 기준으로 정리한다. 시간 초과 여부로 다른 수를 선택하면 기기마다 결과가 달라지므로 고정 후보 수·노드 수로 제한하며, 시간은 성능 측정에만 사용한다.

리플레이는 `rulesVersion + contentHash + initialState + orderedCommands`로 복원한다. 초기 배치·난이도·장비·목표 상태까지 `initialState`에 포함한다. 현행 약화 성공은 저장한 `rngSeed`와 revision·시전자·대상·마법 ID의 고정 판정을 사용한다. seed만으로 전체 상태를 복원하지 않고 초기 상태와 전체 명령도 함께 검증한다. 미리보기는 시드를 소비하지 않는다. 저장 시각·연출 시간은 상태 해시에서 제외한다.

P03a rulesVersion 0.3의 기록은 봉화 차단 153명령과 정면 방어 160명령이며, 두 경로 모두 9라운드·호송 HP 10·아군 12기 생존으로 끝났다. S01b는 미라의 학습 마법을 교체하고 배치·기존 능력치는 유지하므로 같은 로그를 회귀 기준으로 사용한다. 현행 0.8에서의 실행 결과는 [개발 인수인계](handoff.md)에 기록한다. 자동 경로 검증이 사람 플레이·재미·밸런스 검증을 대신하지 않는다.

## 8. 저장과 진행 안전성

현행 P04는 최신 자동 저장·직전 정상 저장·JSON 파일 백업까지 구현했다. 저장 형식/검증은 schema와 web이 담당하고 코어 apply 전체 재현을 비교한다. 자동 행동 중 복구를 위한 continuation을 추가했다. 기여·성장·시나리오 보상 장부는 S04/S05에서 추가했다. 아래의 수동 3슬롯·장 준비 체크포인트·캠페인 진행과 마이그레이션은 후속 설계다.

S04/S05의 실행 규칙은 `0.7`이며 저장 형식 버전은 1이다. 상태 효과·기한·참의 원래 진영·지형 변경·인벤토리·시드는 필수 저장 필드이고, 장착·소환 소유·재행동 적용 라운드·준비 명령·텔레포트 도착 칸도 엄격히 검증한다. 지휘관 진행과 지속 명부, 기여·피해/회복 상한·정산·보상한 시나리오 ID·출격 시작 revision 및 `promote`·`reclass`·`deploy` 명령도 필수 상태와 엄격한 명령 스키마로 저장한다. 이전 0.2~0.6과 다른 콘텐츠 버전의 저장은 자동 변환하지 않는다. 읽기는 기존 슬롯을 변경하지 않으며 정상 슬롯이 없으면 자동 덮어쓰기를 중지한다. `기존 저장 원본 백업`은 최신·직전 JSON을 그대로 읽어 내보내고 현재 전투·저장을 바꾸지 않는다. 필요한 원본을 백업한 뒤 `현재 전투 다시 저장` 또는 초기화로 새 저장을 시작할 수 있다. 원본 백업은 현재 버전으로의 복구나 변환을 보장하지 않는다.

후속 저장 확장안은 로컬 IndexedDB의 수동 3슬롯 + 최신 자동 저장 + 직전 정상 자동 저장 + 장 준비 체크포인트다. 현행은 최신·직전 정상 자동 저장을 제공한다. 확정 행동과 페이즈 전환 경계에서 저장한다. 진행 상태와 해당 명령 로그, 마지막 정산 ID를 하나의 트랜잭션으로 기록한다. 이전 쓰기가 완료되기 전에 새 저장이 덮어쓰지 않도록 직렬 큐를 쓴다.

| 저장 필드                                | 목적                                                   |
| ---------------------------------------- | ------------------------------------------------------ |
| schemaVersion, rulesVersion, contentHash | 형식·규칙·콘텐츠 호환성 구별                           |
| revision, lastCommandId                  | 입력·복구 중복 방지                                    |
| campaign, preparationCheckpoint (후속)   | 장·계약·정식 준비 체크포인트                           |
| battle                                   | 라운드·페이즈·유닛·행동권·목표·트리거·보류 증원        |
| battle.progression                       | 지휘관 명부·EXP 상한·성장 정산·시나리오 보상 중복 방지 |
| initialState, commands                   | 전투 재현                                              |
| updatedAt, checksum                      | 사용자 선택용 시간·손상 탐지, 치팅 인증 용도 아님      |

현재 상태와 직전 정상 상태의 복구를 지원하며 장 준비 체크포인트 복구는 후속이다. 브라우저가 저장을 거부하거나 용량이 부족하면 “저장 실패”를 화면에 유지하고 파일 내보내기를 제공한다. 저장 성공 전에는 성공 아이콘을 표시하지 않는다. 가져오기는 스키마와 참조 ID를 검증하고 미지원 버전이면 기존 슬롯을 덮어쓰지 않는다.

현행 정산은 `battle.progression.rewardedScenarioIds`의 시나리오 ID로 최초 승리만 보상한다. 성장 기록은 살아 있는 전장 유닛과 별도 명부로 보존하여 전투불능 지휘관도 잃지 않는다. 패배 시 전투 기여를 폐기하고 재도전은 기존 성장·장비를 유지한다. 승리 뒤 재연습은 성장 명부·소유 아이템·보상 장부·전역 명령/revision을 유지하고 전장 임시 상태만 초기화한다. 클리어 직후 저장·새로고침으로 보상을 다시 받지 않아야 한다. 재연습·재도전에서도 전역 명령 1,024개 상한을 공유하므로 한 저장 기록의 무제한 반복은 보장하지 않는다. 캠페인 도입 뒤 `campaignId + chapterId` 정산 키와 준비 체크포인트로 확장한다.

콘텐츠 업데이트 중인 저장은 버전을 보고 마이그레이션하거나 해당 콘텐츠를 유지해 이어간다. 대응이 없으면 자동 변환하지 않고 파일 백업과 장 준비로 돌아가는 선택을 제공한다. 클라우드·랭킹은 이 구조 검증 이후 별도 설계한다. 향후 서버 검증은 클라이언트가 조작한 초기 상태를 신뢰하지 않는 것부터 시작해야 한다.

## 9. 구현 검증 기준

코어 테스트는 전투 문서의 숫자·처리 순서·잘못된 명령 불변성을 확인한다. 콘텐츠 검증은 ID 중복·참조 누락·전직 도달성·고용 병종 존재·배치 중첩·맵 밖 좌표·증원 예고·목표 시간·유닛 상한을 확인한다. 지도 경로 검증으로 보너스 제한 시간 안에 도달 가능한지도 검사한다.

마법은 [S01-M01~M06](combat-rules.md#s01-마법-수용-사례)의 일반 계산·원자성·재현과 [S01b-M01~M04](combat-rules.md#s01b-마법-수용-사례)의 반경·부대·자기 중심·특효를 확인한다. 콘텐츠 검증은 마법 정의·중복 ID·학습 참조·지휘관 제한·반경/특효 필드 조건을 검사한다. 브라우저에서는 마법 종류 선택 → 중심과 전체 대상 예측 → 확정·취소 → 기본/상세 연출 → 새로고침 복구를 확인한다. S02-M01~~M06·S03-E01~~E04는 상태·참·지형·재배치·재행동·소환·장착·준비와 저장을 검증하며, S04-X01~~X04·S05-C01~~C04는 기여 상한·EXP 장비·승리 정산·다중 레벨업·학습·전직·룬스톤·재출격·저장을 검증한다.

브라우저 검증은 새 게임 → 한 전투 승리 → 성장 정산 → 저장 → 재실행 → 같은 맵 재연습의 현행 흐름과, 행동 연출 도중 새로고침·저장 실패·파일 가져오기 실패를 확인한다. 다음 장 진행·캠페인 보상은 이후 검증 대상이다. 성능 예산은 production 빌드에서 측정한다. 자동 검증과 별도로 사람이 실제 전술·도트 가독성을 확인한다.

초기 골격에 Vitest(코어), Playwright(브라우저), 콘텐츠 검증 CLI와 명령 로그 재현 CLI를 추가했다. 실제 검증 대상과 실행 명령은 README 및 [개발 인수인계](handoff.md)를 따른다. 이 설계 문서의 모든 수용 기준을 충족한 상태는 아니다.

## 0.8 구현 상태 갱신

`practice`와 `operation`은 canonical 초기 상태와 IndexedDB 키를 실행 규칙·모드별로 분리한다. 기본 DB/형식 버전은 유지하고 수동 3슬롯·최신/직전·출격 준비 키를 사용한다. 수동 슬롯·가져오기·준비 복구는 체크섬과 전체 명령 재생으로 검증한다. 준비 체크포인트는 전투 직전까지의 완전한 명령 prefix이며 임의 스냅샷을 새 초기 상태로 신뢰하지 않는다. 0.7 이하 원본은 기존 키에 보존하고 별도 백업 버튼으로 내보낸다.

저장 창의 준비 복구는 장비·고용·구매를 마친 마지막 준비로 돌아간다. 정식 패배의 재도전은 경제의 준비 진입 체크포인트로 돌아가 이번 구매·편성·전직까지 취소한다. 두 동작 모두 이후 행동·보상을 반복 수령하지 않도록 기록에 맞는 상태로 복원한다. 명령 1,024개에 도달하면 자동 페이즈를 중지하고 백업과 저장 복구를 제공한다. 저장 실패로 최신 진행이 디스크에 없을 때 모드 전환으로 이를 버리지 않는다.

전장에는 물리 위협 토글과 지휘 임시 위치 조회, 50/100/150% 줌, 지도 포커스의 방향키·Space·WASD·Home 조작을 제공한다. 코어 조회의 범위를 화면에 명시하고 모달 키 입력이 전투 명령으로 전달되지 않게 한다. [코어 성능 측정](../artifacts/performance-core.json)은 `pnpm perf:core`로 재생성한다. 해당 측정은 Node의 합성 42기 전장으로서 실제 브라우저 시작·저장·마법 AI·기기별 프레임 품질을 대신하지 않는다. 아래 전체 제품 성능 예산과 사람 플레이 검증 중 미측정 항목은 별도로 남는다.
